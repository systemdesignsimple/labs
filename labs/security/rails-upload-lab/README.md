# rails-upload-lab lab: image upload checks and ImageMagick policy.xml, check and fix

Article: `rails-imagemagick-upload-flaw-check-and-fix`. News source: The Hacker News, 2026-11-04,
https://thehackernews.com/2026/11/critical-rails-flaw-lets-attackers.html. For the CVE number and the affected and
fixed versions, use the official record: the Rails security announcement (rubyonrails.org, "Security" category) and
the GitHub security advisory on `rails/rails`. This lab does not depend on those details. It tests the upload
conditions that make an image-processing bug reachable, and the checks that close them.

## Question

Your app accepts image uploads and resizes them with an image tool (ImageMagick through MiniMagick, or libvips). The
upload check looks at the file name or the `Content-Type` the browser sent. The image tool does not care about either:
it picks the format from the bytes inside the file. So what does your tool actually get handed, and which check
makes sure it only ever sees the formats you meant to accept? And does your server's `policy.xml` back that up?

## How to run

```
NODE_NO_WARNINGS=1 node labs/security/rails-upload-lab/rails-upload-lab.mjs
```

Node.js 22, no npm packages, no network, no ImageMagick needed. Throwaway files are written to a temp dir and deleted
at the end. Finishes in under a second. Every file is generated by the run (a small PNG writer and reader built on
`node:zlib`), so every run prints the same table (only the date in the header changes). The non-image files only
contain a format header and a comment, nothing that draws or runs anything.

## What it does

**Part A, upload pipeline.** Each throwaway upload goes through two checks:

- **unsafe**: accept when the name contains `.png`, `.jpg` or `.gif` (no end anchor) or the `Content-Type` starts with
  `image/`, then pass the original bytes on. A small magic table stands in for the image tool and reports which format
  it would read the bytes as.
- **fixed**: ignore the name and `Content-Type`; the magic bytes must be PNG (the allowlist); read width and height
  from the header and reject anything over 40 MP before decoding; decode the pixels and re-encode a fresh PNG; store it
  under a server-chosen name. The run checks that the re-encoded pixels are identical to the original.

**Part B, policy.xml self-check.** Two throwaway `policy.xml` files: one with no rules (how many installs ship), one
locked down for an upload service. A small reader applies the rules the way ImageMagick 7 does (in order, last
matching rule decides) and reports what each policy allows. It also looks for ImageMagick and its `policy.xml` on this
Mac, read-only, and prints the same check for it if found.

## What it shows

| test | unsafe | fixed |
|---|---|---|
| `.png` / `.jpg` / `.gif` name with SVG, MVG, PostScript or MSL inside | accept, tool reads SVG / MVG / PS / MSL | reject: content is ... |
| double extension `cat.png.svg` | accept, tool reads SVG | reject |
| `notes.txt` sent as `image/png` | accept, tool reads TEXT | reject |
| real PNG + 49 bytes after the end marker | accept, extras 49 B stored | accept, extras 0 B |
| real PNG + metadata text chunk (fake GPS) | accept, extras 51 B stored | accept, extras 0 B |
| header claims 50000x50000 | accept, tool would allocate 10 GB | reject: > 40 MP |
| three normal PNGs (RGBA avatar, `.PNG` banner, odd name and generic type) | accept | accept, same size, same pixels |
| policy.xml: MVG, MSL, SVG, PS, EPS, PDF, TEXT, URL, HTTPS coders | allowed | denied |
| policy.xml: `@file` indirect reads, delegates, area limit | allowed / no limit | denied / 40MP |
| policy.xml: PNG, JPEG, GIF, WEBP | allowed | allowed |

Result: reproduced 21/21, blocked 21/21, normal inputs unchanged 7/7. Full output in `last-run.txt`.

The cause, in one line: the check looks at the label (name, `Content-Type`), the image tool looks at the content, and
a policy with no rules lets the tool use every format it knows.

## How to spot it in your own code

- Validation by file name: `File.extname`, `ends_with?('.png')`, a regex without `\z` / `$`, or the `content_type`
  that came from the browser. In Rails Active Storage, check whether your validation uses the type detected from the
  bytes (`blob.content_type` after identification / analysis) or the one the client declared.
- Variants or thumbnails generated straight from the original upload, with no format allowlist in front.
- `config.active_storage.variant_processor` set to `:mini_magick` on servers whose `policy.xml` you have never read.
- Original uploads served back as-is (they keep metadata such as GPS and any bytes after the image).
- No width / height / area limit anywhere before decoding.

## The fix

- Update Rails (and ImageMagick / libvips) to the fixed versions listed in the official advisory.
- Allowlist by magic bytes, not by name or `Content-Type`. Reject anything else before any image tool sees it.
- Check dimensions from the header before decoding; set limits.
- Re-encode to a fresh file and serve that, under a name your server chose.
- Lock down `policy.xml` on servers that process uploads:

```xml
<policymap>
  <policy domain="resource" name="width" value="8KP"/>
  <policy domain="resource" name="height" value="8KP"/>
  <policy domain="resource" name="area" value="40MP"/>
  <policy domain="resource" name="memory" value="256MiB"/>
  <policy domain="delegate" rights="none" pattern="*"/>
  <policy domain="filter" rights="none" pattern="*"/>
  <policy domain="path" rights="none" pattern="@*"/>
  <policy domain="coder" rights="none" pattern="*"/>
  <policy domain="coder" rights="read|write" pattern="{PNG,JPEG,GIF,WEBP}"/>
</policymap>
```

Only list the formats your app really accepts.

## How to test the fix

- On your own servers, read-only: `magick -version` (or `convert -version`) and `magick -list policy`. The list should
  show the coder rules above and your resource limits. `bundle exec rails -v` and `bundle list | grep -i -E "rails|mini_magick|image_processing|ruby-vips"`
  give the versions to compare with the advisory.
- Copy the rows of this lab into your upload tests: each mismatched file must be rejected, each normal image must
  still upload and look the same, and stored files must have 0 bytes of extras.
- Re-run this lab after changing the checks: `RESULT: FIX WORKS` means every row behaved.
